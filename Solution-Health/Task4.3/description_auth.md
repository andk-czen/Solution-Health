# Схема аутентификации мобильного приложения

## Выбранный протокол
Для аутентификации пациентов применяется OAuth 2.0 совместно с OpenID Connect (OIDC) по схеме Authorization Code Flow с расширением PKCE (Proof Key for Code Exchange, RFC 7636). Это отраслевой стандарт именно для мобильных приложений.
Мобильное приложение относится к категории публичных клиентов: его код распространяется через магазины приложений и может быть проанализирован злоумышленником, поэтому встроить в него клиентский секрет невозможно. PKCE решает эту проблему: приложение генерирует случайное значение code_verifier и отправляет в запросе авторизации только его хеш (code_challenge). Даже если перехватить код авторизации, обменять его на токены без исходного verifier не получится.
Принципиально важно, что учётные данные вводятся только на стороне Identity Provider в системном браузере, а не в формах самого приложения. Приложение никогда не видит пароль пациента. Дополнительно на входе применяется второй фактор — одноразовый код по SMS, что критично для доступа к медицинским данным.

## Способ передачи токена
Access-токен передаётся в HTTP-заголовке Authorization: Bearer <access_token> поверх TLS 1.3. Токен имеет формат JWT, подписан Identity Provider и содержит идентификатор пациента (sub), срок действия и набор разрешений (scope).
Категорически запрещено передавать токен в параметрах URL или в строке запроса: такие значения попадают в логи серверов, историю браузера и заголовки Referer, то есть фактически утекают в открытом виде.

## Параметры токенов
- Access-токен - короткоживущий, срок действия 15 минут. Компрометация ограничена узким временным окном.
- Refresh-токен - долгоживущий, с обязательной ротацией при каждом обновлении. Повторное использование уже погашенного refresh-токена трактуется как признак кражи и приводит к отзыву всей цепочки токенов устройства.
- Хранение токенов - только в защищённом хранилище операционной системы: iOS Keychain или Android Keystore. Использование обычных настроек приложения (SharedPreferences, UserDefaults) недопустимо.
- Локальная разблокировка приложения - по биометрии или PIN-коду, чтобы доступ к сохранённой сессии был закрыт при физическом доступе к устройству.

## Проверка на стороне API Gateway
Каждый запрос проходит валидацию на едином входе. API Gateway проверяет подпись токена по публичным ключам Identity Provider (JWKS), срок действия (exp), издателя (iss), аудиторию (aud) и наличие необходимых разрешений.
Ключевое правило, устраняющее выявленную уязвимость подмены сессии (SD-007, «врач видит чужого пациента»): идентификатор пациента извлекается исключительно из токена, а не из параметров запроса или тела сообщения. Даже если злоумышленник подставит чужой идентификатор в запрос, сервер его проигнорирует и вернёт данные только того пациента, которому принадлежит токен. Проверка принадлежности ресурса выполняется на сервере при каждом обращении.
