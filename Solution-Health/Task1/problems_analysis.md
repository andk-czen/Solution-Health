# Задание 1. Анализ текущей интеграционной архитектуры

## Цель
Описать системные проблемы и риски, которые могут помешать успешному запуску мобильного приложения «Здоровье+», сфокусировавшись на надёжности интеграций, масштабируемости и других критических аспектах.

## Выявленные проблемы и влияние на мобильное приложение

| # | Проблема | Признаки | Влияние на мобильное приложение |
|---|----------|----------|--------------------------------|
| **1** | **Ненадёжная доставка результатов анализов (LIS → CRM) из-за сбоев FTP** |  Jira INT-002: FTP-загрузка падает с ошибкой 425, требуется ручное восстановление<br> Jira INT-008: Дублирование XML-файлов, в CRM попадают дубли анализов<br> Jira INT-011: Неактуальные анализы — LIS передал, а CRM не обновила (застряло в очереди)<br> Service Desk SD-005: Утром не видны анализы, загруженные ночью — FTP-скрипт падал из-за тайм-аута<br> Jira INT-009: Репликация БД для чтения (блокировки) |  Пациенты не видят результаты анализов в приложении в режиме реального времени<br> Кол-центр перегружен звонками с вопросами о статусе анализов (цель — снизить на 30%, но ситуация ухудшится)<br> Врачи работают с неактуальными данными<br> Подрыв доверия к приложению: пациенты ожидают онлайн-доступ к результатам, но получают задержки до 2 часов<br> Риск для регуляторных соответствий (MTOPS/ФЗ-152 — персональные и медицинские данные) |
| **2** | **Деградация производительности 1С:Полисы на пиковых нагрузках** |  Jira INT-003: Проверка полиса падает с ошибкой 503 при >50 rps<br> Service Desk SD-001: Проверка полиса зависает на 30+ секунд, помогла только перезагрузка службы<br> Service Desk SD-008: При записи появляется «Полис недействителен» — 1С вернул null, через 5 минут повтор — успех<br> Синхронная проверка полиса в цепочке оплаты блокирует весь процесс |  Мобильное приложение не выдержит целевые 500 одновременных пользователей (MVP) и 50 000 (финальное решение)<br> Цепочка «запись → проверка полиса → оплата» блокируется на этапе 1С, создавая каскадные таймауты<br> При пиковой нагрузке (вечера, выходные) приложение становится недоступным для ключевой функции<br> Невозможность достичь SLA 99.95% доступности |
| **3** | **Ненадёжность платёжного шлюза: двойные списания и потеря статуса** |  Jira INT-001: При таймауте деньги списываются, статус платежа не фиксируется<br> Jira INT-005: Отсутствие идемпотентности — дубли записей при повторных POST<br> Service Desk SD-002: Пациент оплатил, но ошибка «Booking not found» для paymentID<br> Service Desk SD-009: Двойное списание денег — дважды списали при оплате<br> Синхронный REST API без retry-логики и idempotency-ключей |  Финансовые потери пациентов: двойные списания подрывают доверие к приложению критически<br> Юридические риски: нарушение требований платежных систем (PCI DSS), штрафы от банків<br> Потерянные платежи: деньги списаны, но запись не создана — необходимо ручное разрешение конфликтов<br> Репутационный ущерб: один инцидент с двойным списанием может стать вирусным |
| **4** | **Отсутствие компенсирующих транзакций** |  Service Desk SD-003: Дубль записи на один слот — пациент дважды нажал «Записаться»<br> Service Desk SD-002: Оплата прошла, но подтверждение не пришло<br> Синхронная цепочка: бронирование → проверка полиса → оплата → резервирование в LIS<br> Нет механизма отмены частичного выполнения при сбоях |  Дублирование записей: пациенты видят несколько одинаковых записей, путаются в статусе<br> «Зависшие» платежи: деньги списаны, но запись не создана и не отменена<br> Невозможность обеспечения консистентности данных между системами<br> Нарушение бизнес-процессов: врач видит запись, но лаборатория не получила запрос на анализ |
| **5** | **Отсутствие API Gateway и документации (OpenAPI)** |  Jira INT-010 (Epic, Critical): Разработать API Gateway с rate limiting и идемпотентностью<br> Отсутствие спецификаций API для существующих endpoints<br> Jira INT-006: SQL-инъекция в поле поиска пациента на веб-портале<br> Интеграция мобильного приложения с разнородными системами без единой точки входа |  Мобильное приложение не имеет единого безопасного канала для всех API-вызовов<br> Невозможность применения единых политик: аутентификация, rate limiting, мониторинг<br> Высокие риски безопасности: SQL-инъекции, отсутствие защиты от brute-force<br> Затруднённая разработка: фронтенд и бэкенд не имеют единого контракта, высокая вероятность регрессий |
| **6** | **Критические уязвимости безопасности** |  Jira INT-006: SQL-инъекция в поле поиска (веб-портал)<br> Service Desk SD-007: Врач видит чужого пациента — подмена сессии (CSRF/Session fixation)<br> Данные передаются без должного шифрования<br> Отсутствие защиты от IDOR (Insecure Direct Object References) |  Утечка персональных и медицинских данных пациентов (ФЗ-152, международные требования)<br> Подмена сессии: злоумышленник получает доступ к медицинским картам<br> Отсутствие аутентификации для мобильного приложения (нет OAuth2/OIDC)<br> Невозможность прохождения аудита безопасности перед запуском |
| **7** | **Синхронные интеграции между сервисами (каскадные отказы)** |  Все текущие интеграции синхронные (REST, SOAP)<br> Jira INT-007 (Critical): Отсутствие distributed tracing — сложно найти корень сбоя<br> Таймауты одной системы блокируют весь цепочку вызовов<br> Service Desk SD-004: Приложение виснет 10 секунд при оплате |  Сбой одной системы (1С, LIS, платёжный шлюз) → отказ всего мобильного приложения<br> Невозможность достижения SLA 99.95% из-за зависимости от ненадёжных внешних систем<br> Каскадные отказы при пиковых нагрузках: 500 пользователей MVP → весь стек зависает<br> Сложность отладки: без tracing время восстановления (MTTR) превышает 1 час |
| **8** | **Отсутствие мониторинга и наблюдаемости** |  Jira INT-007: Отсутствие distributed tracing<br> Логи разбросаны по разным системам (LIS, CRM, 1С, платежный шлюз)<br> Нет метрик задержек, алертов на критические ошибки<br> Jira INT-004: Документировать лимиты RabbitMQ |  Невозможность быстрой диагностики проблем при запуске приложения<br> MTTR > 1 часа: пользователи покидают приложение при ошибках<br> Скрытые деградации: система работает, но медленно, без оповещений<br> Отсутствие basis для performance-тестирования и масштабирования |
| **9** | **Архитектурная зависимость от legacy-систем** |  LIS: SOAP, FTP для загрузки данных с оборудования (устаревшие технологии)<br> 1С: монolith, сложно модифицировать<br> Тесная связность между сервисами (изменения в LIS требуют перестройки интеграций)<br> Service Desk SD-001: Помогла только перезагрузка службы 1С |  Высокая стоимость и длительные сроки внедрения новых функций в приложении<br> Любые изменения в LIS или 1С могут сломать интеграции с мобильным приложением<br> Невозможность быстрого масштабирования: legacy-системы не поддерживают горизонтальное масштабирование<br> Привлечение узких специалистов (1С, SOAP) увеличивает стоимость поддержки |
| **10** | **Отсутствие обработки пиковых нагрузок** |  Текущие системы спроектированы на 100-200 пользователей<br> Рост уникальных пациентов на 40% за последний год<br> 5 новых центров открыты, нагрузка продолжает расти<br> Целевой показатель: 50 000 пользователей в пик (MVP: 500) |  Приложение недоступно в часы пик (вечера 19:00-21:00, выходные)<br> Потеря пациентов: не могут записаться к врачу → уход к конкурентам<br> Невозможность достижения цели по 50 000 пользователей<br> Нарушение SLA: отклик > 1 секунды для 99% запросов недостижим без балансировки нагрузки |
| **11** | **Отсутствие идемпотентности операций записи и оплаты** | INT-005 (дубли записей при повторных POST в «Расписании»); SD-003 (двойное нажатие → две записи); INT-010 (идемпотентность вынесена в эпик API Gateway); SD-009, INT-001 (двойное списание / несогласованность оплаты) | В мобильном приложении повторные тапы, ретраи при плохой сети и таймауты неизбежны. Без идемпотентности - массовые дубли записей и двойные списания, рост нагрузки на колл-центр вместо её снижения на 30%, репутационные и финансовые претензии |
| **12** | **Проблемы масштабируемости и блокировки в БД** | INT-009 (нужна реплика на чтение - блокировки в «Расписании»); INT-003 (деградация 1С); отсутствие горизонтального масштабирования Legacy-компонентов | Пиковая нагрузка MVP (500 пользователей вечером/в выходные) и финал (50 000, отклик <1 с для 99%) недостижимы, пока «Расписание», LIS и 1С не масштабируются. БД-блокировки → таймауты записи в час пик |

## Критические блокировки для запуска MVP (3 месяца)

| Приоритет | Проблема | Обоснование |
|-----------|----------|-------------|
| **P0** | Безопасность (SQL-инъекции, CSRF, отсутствие шифрования) | Без решения невозможно запустить приложение — обработка медицинских данных требует compliance |
| **P0** | Надёжность платежей (двойные списания, потеря статуса) | Финансовые потери и юридические риски (PCI DSS) |
| **P0** | API Gateway (rate limiting, идемпотентность, единый вход) | Jira INT-010 — Epic Critical, без него нет защиты от перегрузок |
| **P1** | Надёжная доставка результатов анализов | Пациенты не получат ключевую функцию MVP — результаты в приложении |
| **P1** | Масштабируемость 1С (кэширование, асинхронная проверка полиса) | 500 одновременных пользователей (MVP) не будут обслуживаться |
