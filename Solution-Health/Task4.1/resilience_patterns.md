# Задание 4.1. Реализация отказоустойчивости интеграции ИТ-систем

## 1. Параметры отказоустойчивости

### Таблица с параметрами для 1С и платёжного шлюза

| Параметр | 1С:Полисы | Платёжный шлюз | Обоснование |
|----------|-----------|----------------|-------------|
| **Timeout** | 2 секунды | 5 секунд | 1С отвечает медленнее (monolith, перегрузка), но таймаут должен быть агрессивным чтобы быстро переходить к fallback (Redis-кэш). Платёжный шлюз — внешний провайдер, стандартный timeout 5 сек для финансовых API. |
| **Попытки (Retries)** | 2 | 2 | Ограниченное число попыток для быстрого падения в CB. 1С не должна блокировать поток надолго. |
| **Интервал retry (Backoff)** | Exponential: 100 мс, 500 мс + jitter ±20% | Exponential: 500 мс, 2000 мс + jitter ±20% | 1С — внутренняя система, быстрый backoff позволяет быстро восстановить. Платёжный шлюз — внешний, более длинный backoff чтобы не перегрузить провайдера. |
| **Circuit Breaker Error Threshold** | 80% | 95% | 1С стабильно падает при >50 rps (20-30% ошибок), поэтому CB срабатывает раньше (80%). Платёжный шлюз надёжен (1-2% ошибок), CB срабатывает только при реальной проблеме (95%). |
| **Circuit Breaker Recovery (Half-Open)** | 30 секунд | 60 секунд | 1С восстанавливается медленно (нужна перезагрузка), поэтому проверка реже. Платёжный шлюз обычно восстанавливается за минуты. |
| **Fallback** | Возврат кэшированного значения из Redis (Cache-Aside) | Retry backup + deny-after-fallback | Для 1С — кэш полиса в Redis (TTL 24 часа). Для платёжного шлюза — нет кэша платежей, retry с idempotency key. Если CB OPEN и retry исчерпаны → отклонить операцию с понятной ошибкой. |
| **Bulkhead** | Да: отдельный thread pool (size=50) | Да: отдельный thread pool (size=30) | Изоляция: сбой 1С не блокирует другие операции (запись, аналиты). Сбой платёжного шлюза не блокирует навигацию в приложении. |
| **Idempotency** | Нет (read-only операция) | Да: UUID-based idempotency key | Проверка полиса — чтение, не требует идемпотентности. Платёж — требует идемпотентного ключа (sagaId + "_payment"). |

## 2. Обоснование выбора ИТ-системы для приоритетного внедрения circuit breaker

### Для какой системы CB более критичен: 1С:Полисы

| Критерий | 1С:Полисы | Платёжный шлюз |
|----------|-----------|----------------|
| **Частота отказов** | 20-30% (INT-003, SD-001, SD-008) | 1-2% |
| **Влияние на бизнес** | Блокирует ВСЕ записи (критическая цепочка) | Блокирует только оплату |
| **Время восстановления** | Медленное (перезагрузка, часы) | Быстрое (минуты) |
| **Наличие fallback** | Да (Redis-кэш полисов) | Частично (retry с idempotency) |
| **Приоритет CB** | **ВЫСШИЙ** | СРЕДНИЙ |

**Вывод:** Circuit Breaker критически важен для 1С:Полисы по следующим причинам:

1. **Частота отказов в 15-20 раз выше** (20-30% vs 1-2%). Без CB каждый запрос к 1С рискует таймаутнуть на 30 секунд (SD-001), блокируя весь процесс записи.
2. **Каскадный эффект:** Проверка полиса — шаг 2 в SAGA (резервирование → проверка полиса → оплата → финализация). Сбой на шаге 2 отменяет ВСЮ цепочку.
3. **Медленное восстановление:** 1С требует перезагрузки службы, что занимает часы. CB защищает 1С от перегрузки, снижая количество запросов на 90%.
4. **Наличие fallback:** Redis-кэш позволяет вернуть результат проверки полиса за <10 мс даже при недоступности 1С.

### Механизм работы Circuit Breaker для 1С

**Circuit Breaker: 1С:Полисы**

| Состояние | Поведение | Условие перехода (для 1С)|  
|----------|-----------|----------------|
| Closed (замкнут) | Вызовы проходят к 1С в обычном режиме. Прокси считает долю ошибок и медленных ответов в скользящем окне. | При доле сбоев более 50% в окне из 20 вызовов (учитываются коды 503, таймауты и ответы дольше 2 с) -> переход в Open. |
| Open (разомкнут) | Вызовы к 1С не выполняются вовсе - мгновенный отказ (fail fast) и переход на fallback: кэш полиса либо статус «полис на проверке». | Удерживается 30 секунд, после чего -> Half-Open. |
| Half-Open (полуоткрыт) | Пропускается ограниченная серия пробных вызовов (5 штук), остальные по-прежнему уходят в fallback. | Все пробные успешны -> Closed (движение восстановлено). Есть сбои -> снова Open на следующие 30 с. |


## 3. Архитектурное решение для снижения нагрузки на 1С

Асинхронная модель на основе Kafka топиков позволяет нормализовать поток запросов к 1C и обрабатывать запросы в пределах возможностей системы.
Но для целей сокращения времени ожидания и решения проблемы каскадного влияния изменения контрактов со стороны 1С требуется подготовка системы перед 1С которая реализует две функции:
- ACL слой между внутренними системами и 1С
- Слой кеширования доступных полисов

В таком случае мы достигаем существенного снижения нагрузки на 1C через самостоятельную валидацию на основе внутреннего кешированного справочника и обращаемся к 1С только в случае промаха поиска в кеше.

```plantuml
@startuml
title C4 Level 1: Снижение нагрузки на 1С — кеширование, ACL и асинхронная обработка

!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Context.puml

LAYOUT_WITH_LEGEND()
LAYOUT_TOP_DOWN()

Person(patient, "Пациент")

System(mobile_app, "Мобильное приложение", "Инициирует сагу записи")
System(api_gateway, "API Gateway")

System(saga_orch, "Booking Orchestrator", "Координирует шаги саги.\nПубликует команды в Kafka")
System(kafka, "Kafka")

System(policy_svc, "Policy Verification Service", "ACL и кеширующий слои")
System(redis, "Redis", "Слой кеширования")

System_Ext(sys_1c, "1С: Полисы")

Rel(patient, mobile_app, "Создание записи", "HTTPS")
Rel(mobile_app, api_gateway, "POST /api/v1/appointments")
Rel(api_gateway, saga_orch, "Запуск саги", "REST")

Rel(saga_orch, kafka, "команда запроса верификации")

Rel(kafka, policy_svc, "команда запроса верификации")

Rel(policy_svc, redis, "GET/SET полисов")

Rel(policy_svc, sys_1c, "Верификация полисов")
Rel(policy_svc, kafka, "событие ошибки верификации")
Rel(kafka, saga_orch, "Результат верификации")

@enduml
```


### Стратегия Cache-Aside

| Слой | Механизм | Эффект |
|------|----------|--------|
| **L1: Redis (Cache-Aside)** | Результат проверки полиса кэшируется на 24 часа. Повторные запросы обслуживаются за <5 мс без обращения к 1С. | **80-90% запросов обслуживаются из кэша** |
| **L2: Circuit Breaker** | При 80% ошибках CB открывается, все запросы 30 секунд обслуживаются из кэша или отклоняются. | **100% защита от перегрузки 1С** |
| **L3: Async background refresh** | Background worker обновляет кэш полисов каждые 6 часов для активных пациентов. | **Снижает risk stale данных** |
| **L4: Anti-Corruption Layer** | ACL трансформирует формат данных 1С в формат CRM, изолируя бэкенд от особенностей legacy. | **Гибкость при изменениях в 1С** |
