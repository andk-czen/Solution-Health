# Задание 2. Целевая интеграционная архитектура

Цель задания: спроектировать целевую интеграционную архитектуру ИТ-ландшафта «Здоровья+» для успешного внедрения мобильного приложения.
Для каждой новой интеграции укажите, почему вы выбрали именно этот паттерн, какие архитектурные стили вы использовали и почему. В случае комбинации пропишите, как именно.

*API GAteway, Booking Orchestrator, CRM, Расписание, Payment Service - внутренние сервисы системы, и на схеме уровня L1 располагаются внутри Backend-системы "Здоровье+"

## Интеграции и обоснования

### Мобильное приложение - API Gateway 
Паттерн API Gateway.
Единая точка входа для приложений. Решает текущую проблему из INT-010 (Epic, Critical): "Разработать API Gateway с rate limiting и идемпотентностью при внедрении".

### Веб портал - API Gateway 
Паттерн API Gateway. Единая точка входа. Аналогично взаимодействию "Мобильное приложение -> API Gateway".

### Приложения - Auth Service
Паттерн - Token-based Authentication (OAuth2 Authorization Code + PKCE).
OAuth2 с PKCE это индустриальный стандарт аутентификации мобильных приложений.
Выделенная, централизованная аутентификация пользователей.
Решает проблему текущего веб-портала "риск подмены сессии" (SD-007: "Врач видит чужого пациента").

### API Gateway - Бекенд системы
Стиль интеграции - синхронные запрос/ответ REST API.
Интеграции поддерживают идемпотентные вызовы + Retry, Timeout и Circuit Breaker.

### Booking Orchestrator - 1С:Полисы
Стиль интеграции - асинхронные события через Kafka.
Нагрузка на 1C контролируется консьюмером самостоятельно (буферизация).
Дополнительно нагрузка снижается за счет выделенного слоя кеширования - Policy Verification Service.

### Booking Orchestrator - Расписание (слоты)
Стиль интеграции - асинхронные события через Kafka.
Оркестратор управляет жизненным циклом слота в рамках саги: резервирует слот до оплаты, подтверждает после успешной оплаты, освобождает при сбое через компенсирующую транзакцию.
Аналогично для лаборатории.

### Booking Orchestrator - Payment Service
Стиль интеграции - асинхронные события через Kafka.
Payment Service отвечает только за проведение платежа.

### Payment Service - Платёжный шлюз
Паттерны: Idempotency Key (гарантия не более одного списания) + Persistent State.
Адаптирует запросы для обращения во внешний платежный шлюз, фиксирует результаты обращений в рамках ключа идемпотентности.

### Оборудование - LIS
Стиль интеграции - пакетная выгрузка через FTP.
Оборудование подготавливает единый батч файл, LIS самостоятельно выполняет обработку батча при таймаутах и ошибках.
Выбор обусловлен ограничением: оборудование умеет только выгружать файлы на FTP.

### LIS - CRM
Паттерн - Transactional Outbox при создании результатов анализа.
Transactional Outbox решает проблему — "данные получены, но не доставлены".
Доставка из Outbox в CRM происходит через Kafka т.к. в рамках сценария достаточно временной согласованности. At-least-once гарантия доставки.

### Все backend системы - Distributed Tracing
Паттерн наблюдаемости Distributed Tracing.
Причина - INT-007 (Critical) прямо требует внедрения distributed tracing.
